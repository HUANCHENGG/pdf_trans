# 对抗性审查报告 —— PROJECT_PLAN.md v0.1

> 审查日期：2026-08-28 | 审查方法：红队三视角攻击
> 视角 A·较真终端用户：真实翻车场景推演；视角 B·对抗性输入：边缘/恶意 PDF 与极端用法；视角 C·怀疑论架构师：攻击方案中每一个"假设成立"。
> 分级：P0=推翻性，必须先决；P1=直接威胁验收红线；P2=工程稳健性/体验；P3=备忘。

---

## P0 —— 推翻性问题（先决）

### P0-1 需求自相矛盾：要部署到服务器，却不做任何鉴权
- **攻击**：方案决策 1 是"自用，无账号系统"，需求 7 是"部署在本地和服务器上"。两句话放在一起就是一个公网裸奔的文件上传服务：任何人扫到端口就能上传 PDF、消耗你绑定的大模型 API 余额、塞满磁盘。
- **后果场景**：服务器上线两周，API 账单异常，磁盘被垃圾 PDF 塞满。
- **修复**：必须定义暴露面。选项：① 仅内网/VPN/SSH 隧道访问（保持零鉴权设计）；② 公网部署但加最简单的共享 token（一个环境变量 + 中间件，半天工作量）。二选一，不允许"以后再说"。

### P0-2 "格式不变"与"双语对照"的内在矛盾从未向用户摊牌
- **攻击**：你选了双语对照版，而双语插入译文必然改变原页面——底部内容可能被挤到下一页、目录页码失效、页眉页脚错位。方案一边承诺"格式不变"，一边选了个"必然改变格式"的输出形态，却没有任何一处说明这个代价。
- **后果场景**：M3 交付时你发现目录页码全错、某些页底部内容被裁，认定项目失败——但这其实是双语模式的固有代价，本应在需求阶段就定义清楚。
- **修复**：给"格式保持"下可验收的分级定义，写进方案：
  - **L1 结构不变（红线）**：图片/表格/页面框架位置不变，不丢失、不裁切
  - **L2 排版微变（可接受）**：因译文插入导致的行距、段落间距调整
  - **L3 页面重排（双语模式的固有代价）**：内容被挤到下一页、目录页码漂移——需要明确接受，或接受"目录页码可能不准"这一条写进已知限制
  - 验收时按此分级判定，L3 不算失败。

### P0-3 M0 没有定义 go/no-go 出口，"二开 BabelDOC"决策可能被绑架
- **攻击**：M0 的定位是"验证底座"，但没有回答：如果体检发现 BabelDOC 对密表格 datasheet 的错位率高到不可接受，怎么办？方案没有切换预案，等于把最重要的架构决策押在一个未验证的假设上，且没有失败出口。
- **修复**：M0 写明决策规则。例如：
  - 典型手册 90%+ 页面通过 5 条红线 → 维持二开
  - 表格错位集中出现但可通过配置/预处理解决 → 维持二开，差距清单转入 M2
  - 引擎层面系统性翻车（表格/图片大面积损坏且无配置可救）→ 触发备选评估：pdf2zh_next CLI 路线、或"原位替换自研最小内核"（仅限 v1 范围），重估 2 周
- **配套**：M1 的集成方式不能锁死"Python API 嵌入"一条路——BabelDOC/pdf2zh 的 API 稳定性和可嵌入性本身就是 M0 要验证的事项。备选：CLI 子进程调用（解析 stdout 进度）。方案需写成"API 优先，CLI 子进程兜底"。

## P1 —— 直接威胁验收红线

### P1-1 批处理对齐问题：最经典的翻译管线事故，方案只字未提
- **攻击**：表格单元格里的短文本（"Yes" / "3.3" / "EN pin"）逐条送 API 又贵又没上下文，正确做法是合并成批次。但 LLM 返回时可能合并、拆分、漏译——**返回条数与发送条数对不上，结果回填就会整体错位：第 3 格的译文填进第 5 格，整页表格内容串行**。这是直接命中红线 1 的事故模式，且方案里"分块批处理"四个字完全没有对应的保障机制。
- **修复**：M2 明确"对齐协议"：每段带编号 ID 的请求格式 + 返回解析校验（数量/ID 一致性）+ 校验失败自动降级为逐条翻译 + 对齐失败块标记告警。

### P1-2 静默失败：没文字层的页、乱码编码的 PDF 会被"无声跳过"
- **攻击**：你确认了"原生电子版为主"，但真实电子手册常有混合内容——正文有文字层，某几页插图是纯图片；更隐蔽的是老厂商 PDF 存在 ToUnicode 缺失/损坏，文字能选中但提取出来是乱码。这两种情况如果引擎只是"没有可翻内容所以跳过"，用户会**以为翻译完成了**，实际整页漏翻。静默失败比报错更危险——工程师拿着漏翻的参数表做设计。
- **修复**：M1 加"覆盖度报告"：任务完成时输出每页的"可翻文本量 / 实际翻译量 / 疑似乱码页 / 无文字层页"清单，前端醒目提示异常页。这也顺带成为红线 2/4 的自检数据源。

### P1-3 术语"硬映射"通道没有落实路径，可能是个空头承诺
- **攻击**：方案承诺术语双通道（硬映射 + prompt 注入）。但需追问：BabelDOC 的 glossary 接口到底是什么语义——是强约束替换，还是仅 prompt 注入？（M0 待验证。）若引擎只支持后者，"硬映射"就得自己做，而**译后文本替换会改变文本长度、破坏已排好的版式**——等于自己制造溢出。另外英文词形变化（capacitor/capacitors/CAPACITOR）的匹配策略、替换后与原文框的对齐，都没有定义。
- **修复**：M0 验证 glossary 语义；硬映射的实现定位为"prompt 强约束 + 译后校验告警"而非"译后文本替换"，译后校验发现违反术语表时标记该片段人工复查（或整段重试），不做破坏版式的自动替换。词形匹配规则（大小写不敏感、词边界、复数归一）写入 M2。

### P1-4 表格翻译缺少"列感知"，片段级正则的粒度不够
- **攻击**：电子手册参数表的典型结构：`Pin Name` 列（绝不能翻）、`Pin Description` 列（必须翻）、`Min/Typ/Max` 列（纯数字）。片段级正则能拦住 "PA5" 这种值，但拦不住 "Description" 列头该翻、"Name" 列不该翻的**列级语义**。更糟的是跨页长表（电子手册超常见）：每页重复表头，表头译法不一致就直接踩红线 5。
- **修复**：M2 规则引擎增加"表格列级规则"维度（按列头词匹配整列的不翻译策略）；表头行纳入术语表强制一致。跨页表格效果列入 M0 体检项。

### P1-5 翻译缓存与上下文的矛盾：一词多义被缓存固化
- **攻击**："按文本片段哈希缓存"在省钱的同时会把错误固化：`Ground` 在电源章节译"地"，机械安装章节该译"接地"——第一次翻错，全文档永远错，且二次翻译复用缓存导致修正无效。工程手册一词多义并不罕见（`bank`、`field`、`register bank`）。
- **修复**：缓存 key 挂上"上下文指纹"（前一段哈希 + 所在页 + 是否表格内）；或缓存命中时仍展示"上次译文 + 上下文已变化"提示。至少：术语表更新后可一键失效相关缓存。

### P1-6 双语版式自身可能触发红线 3（溢出遮挡）
- **攻击**：双语模式在原文下方插一行译文，行高增加——密集表格行插入译文后可能压线、遮挡相邻行；页面底部行插入后被挤出可打印区。你把"译文溢出遮挡"列为红线，而输出形态选择本身就在制造这种风险。方案没有任何一处把两者关联。
- **修复**：M0 体检专门观察引擎双语模式在密集表格/页底的表现；若不达标，降级选项：该页退化为单语译文版（页内可配置）。

## P2 —— 工程稳健性与体验缺口

### P2-1 不翻译规则"误杀"无审计：该翻的没翻，用户永远不知道
- 攻击：规则引擎拦了 `V2.0`（版本号被单位规则误伤）、拦了正文里的 `USART1`（其实这句是 "The USART1 receiver wakeup feature..." 该整句翻译）。方案只说"命中即跳过 + 写日志"，没人会去翻日志。
- 修复：跳过内容在结果页汇总展示（"本次共跳过 471 处，抽样 20 处列表"），并提供单页开关（"本页强制全翻"）。

### P2-2 M0 体检样本标准太粗，会漏掉真实的雷
- 现在只有"表格最密的一本"。应补齐维度：双栏/侧边栏排版（ST 应用笔记风格）、横排旋转页、跨页长表、含 ToUnicode 乱码的老 PDF、带权限限制（不允许复制）的加密 PDF、中文文件名/路径（Windows 编码经典坑）。每类至少 1 本，否则 M0 结论以偏概全。

### P2-3 书签/内部链接/目录页码策略空白
- PDF 大纲书签要不要翻？跳转锚点在双语版式下会不会失效？属于"格式不变"需求的一部分，方案未覆盖。默认建议：书签文字一并翻译，跳转锚点依赖引擎行为，列入 M0 观察项，不达标写进已知限制。

### P2-4 "试翻前 N 页"功能缺失
- 翻 500 页手册前先验证质量是最自然的工作流（也最省钱），v1 却没有。上送 M1：上传页加"试翻前 5/10 页"入口。

### P2-5 资源边界全部未定义
- 文件大小/页数上限（200MB、500 页要不要支持？影响内存策略与分块设计）；多个任务同时上传时的行为（建议 v1 串行队列，自用足够，明确写出）；BabelDOC 渲染是 CPU 密集，asyncio 里要丢线程池/进程池，否则进度推送会卡死。本机 Python 3.14 过新，PyMuPDF 轮子支持可能滞后，建议 venv 用 3.12。

### P2-6 成本模型缺失，模型选型建议悬空
- 方案说"100 页几万~几十万 token"却没有落到钱：同样一本手册，国产高性价比模型与顶级模型可能差 10~30 倍。没有每 100 页的成本估算，"翻译缓存省钱""硬映射省钱"都只是口号。M1 加任务级 token 统计时顺带做"按字符数估费"兜底（部分中转站不返回 usage 字段）。

### P2-7 术语表的内容来源与冲突优先级未定义
- 300~500 条预置词表谁来做、以什么为准（行业惯例译法：去耦电容/上拉电阻/阻焊层，而非字面直译）？用户自定义词条与预置词条冲突时谁赢？修复：预置词表以"收录行业惯用译法"为标准在 M2 建设（可参考开源电子词典/社区词表起步）；优先级规则一句话定死：用户自定义 > 项目词表 > 全局预置。

### P2-8 时间盒未声明投入假设
- "6 周"是按全职算还是业余时间算？自用项目通常业余开发，按每周 10~15 小时重估或明确标注假设，避免排期自我欺骗。

## P3 —— 备忘

- API key 明文存 SQLite/配置文件：自用可接受，文档中注明风险边界。
- 金标准手册是厂商版权文件：测试样本目录不入 git（.gitignore）。
- 中文输出字体的嵌入授权：确认引擎默认中文字体为开源授权（思源系列等）。
- 服务器部署时 nginx 反代需关闭 SSE 缓冲（部署文档备忘）。
- 漏译/增译检测：译后对账"原文块数 = 译文块数"，超出阈值告警（成本很低，值得 M2 顺手做）。

## 审查结论

方案的主干（二开 BabelDOC、聚焦电子行业适配层、四阶段里程碑）经过攻击后依然成立，**不需要推翻**。但暴露出：
1. 两处**需求级矛盾**必须在开工前拍板（P0-1 服务器暴露面、P0-2 格式保持分级）；
2. **M0 的决策出口和体检样本标准**需要补齐，否则 M0 会变成走过场（P0-3、P2-2）；
3. 五条红线里，"表格错乱"和"溢出遮挡"各自多了一个方案内未识别的成因（P1-1 批处理对齐、P1-6 双语版式自身），需要在 M0/M2 有对应动作；
4. 若干低成本高价值的功能/护栏（覆盖度报告、试翻 N 页、误杀审计、token 统计）应提前进 M1/M2。
